1. 文档目的与设计原则
1.1 文档目的
本文档将已确认的业务需求转化为可实施的技术方案，作为5人核心开发组进行架构设计、模块开发、接口联调、测试部署和版本验收的共同基线。
1.2 设计原则
1. 业务闭环优先：先完成注册—测评—画像—推荐—计划—复盘，再增加智能增强功能。
2. 确定性业务与生成式能力分离：Spring Boot负责数据和规则，FastAPI负责AI与PDF处理。
3. 轻量可交付：采用模块化单体＋独立智能服务，不引入服务注册中心、Kubernetes等复杂基础设施。
4. 规则优先、AI解释：方向排序由结构化评分产生，大模型只生成解释与草案。
5. 默认安全：最小采集、最小权限、脱敏调用、审计留痕和失败降级。
6. 配置驱动：问卷、方向、权重、能力标签和任务模板尽量通过管理端配置。

8. 数据库设计
8.1 命名与通用字段
表名、字段名使用snake_case；主键统一为bigint或UUID方案中的一种，首版建议bigint雪花ID。
业务表包含created_at、updated_at、created_by、updated_by；需要逻辑删除的表增加deleted。
版本化对象增加version_no、status、published_at。
枚举值在代码和数据库字典中统一，不使用含义不明的数字。
8.2 核心表清单
8.3 关键关联
一个学生可有多个测评会话、画像快照、推荐批次、目标版本和计划版本。
推荐批次必须关联画像快照和规则版本，推荐结果关联具体方向版本。
正式计划关联学生确认的目标版本；AI生成结果仅作为草案来源。
培养方案课程与能力标签为多对多关系，标签关系应包含审核人和版本。
辅导员学生关系作为所有辅导员访问校验的唯一依据。
9. 推荐引擎设计
9.1 三段式流程
1. 规则过滤：依据学生选择的路径、适用专业、方向状态和必要条件筛选候选方向。
2. 结构化评分：根据兴趣、价值观、能力、学业基础、发展倾向和经历计算匹配分。
3. 解释生成：将排序结果和维度差异发送给FastAPI，由大模型生成通俗解释。
9.2 评分模型
Score(direction) = Σ [ weight_i × match(student_i, target_i) ] - penalty

建议初始权重：
兴趣 0.20；职业价值观 0.15；能力基础 0.25；
学业基础 0.15；发展倾向 0.20；经历 0.05。

最终权重存放于配置表，禁止写死在前端或提示词中。
9.3 匹配函数
9.4 可信程度
High：必填数据完整、主要维度一致且第一名与后续方向差异明显。
Medium：数据基本完整，但方向分数接近或部分维度存在冲突。
Low：数据缺失较多、测评未完成或结果冲突明显，应提示继续探索。
可信程度不是统计概率，不显示为“成功率”或“适合率”。
10. AI网关与脱敏设计
10.1 调用链路
Spring Boot创建AI任务
    → 组装最小必要结构化数据
    → 调用FastAPI
    → FastAPI字段白名单过滤
    → 自由文本脱敏
    → 调用公网模型
    → Pydantic校验JSON
    → 安全与长度校验
    → 返回Spring Boot
    → 业务校验并持久化草案
10.2 脱敏规则
10.3 提示词管理
提示词存放于版本化文件或配置表，包含system、task、schema_version和status。
生产环境只允许发布状态提示词；修改提示词须创建新版本。
每次AI调用记录prompt_version和model_name。
提示词明确禁止生成结论性标签，必须输出可选建议和人工复核提示。
10.4 输出校验
使用Pydantic进行必填字段、枚举、数组数量和字符串长度校验。
推荐解释的方向ID必须存在于本次候选列表，禁止模型新增方向。
计划任务数量设上限，避免生成几十项不可执行任务。
输出含敏感词、高风险判断或不支持内容时，替换为安全模板。
11. 培养方案PDF解析设计
11.1 处理流程
1. 管理员上传PDF，Spring Boot保存文件元数据并创建导入任务。
2. FastAPI使用PyMuPDF／pdfplumber提取文本，使用表格工具识别课程表。
3. 按课程代码、课程名称、学期、学分、学时、类别、模块和先修课程映射字段。
4. 生成import_item待审核记录，并保留页码、原文片段和置信标记。
5. 管理员在预览页修改、合并、删除和补录。
6. 教师审核课程能力标签后发布培养方案版本。

12. 接口规范
12.1 REST约定
统一前缀/api/v1；资源使用复数名词；查询使用GET，创建POST，部分更新PATCH，删除DELETE。
分页参数统一为page、size、sort；后端限制最大size。
时间统一使用ISO 8601；数据库使用UTC或统一服务器时区，前端按本地展示。
所有写操作校验Content-Type、身份、权限和业务状态。

15. 开发规范与协作流程
15.1 Git分支
main              # 生产发布
 develop          # 集成分支
 feature/<name>   # 功能开发
 fix/<issue>      # 缺陷修复
 release/<ver>    # 发布准备（可选）
15.2 合并要求
禁止直接向main提交；功能通过Pull/Merge Request进入develop。
每次合并至少一名非作者审查；数据库迁移、权限和AI脱敏代码由技术负责人重点审查。
合并请求应包含功能说明、测试方法、截图或接口示例及影响范围。
单个功能分支尽量控制在2—3天内合并，避免长期大分支。
15.3 完成定义（Definition of Done）
代码完成并通过静态检查；接口或页面符合需求。
包含必要单元测试／接口测试；关键异常场景已验证。
接口文档、数据库迁移和配置说明同步更新。
权限、日志、空状态和错误提示已完成。
已部署test环境并由非开发者按用例验收。
16. 测试方案
16.1 最低自动化测试要求
计分与推荐核心函数的单元测试覆盖主要分支。
登录、注册、提交问卷、获取推荐、确认目标和任务更新的接口回归测试。
FastAPI每个结构化输出模型至少包含成功、缺字段、超长和错误枚举测试。
CI至少执行编译、单元测试和前端构建；部署可先采用手工批准。

安全域 | 设计要求
身份认证 | JWT短期访问令牌；密码使用BCrypt或Argon2；登录失败限制。
权限控制 | RBAC＋资源范围校验；辅导员访问必须验证advisor_student_relation。
传输安全 | 正式试用必须HTTPS；Nginx关闭弱协议；API不在URL携带敏感信息。
输入安全 | 后端参数校验、SQL参数化、文件类型和大小限制、XSS输出编码。
数据安全 | 数据库仅内网端口；备份加密或访问受限；API密钥使用环境变量／密钥文件。
AI安全 | 字段白名单、脱敏、结构化输出校验、提示注入防护和高风险场景转人工。
审计 | 登录、失败登录、查看学生详情、导出、配置发布、权限变更和AI调用记录。
