# 服务器部署提示词（给服务器端智能体一次性输入，即可自动完成部署）

> 使用方式：把本节全文复制，粘贴给服务器上的智能体执行。
> 验收标准：执行完毕后，`docker compose ps` 三个容器均 Up 且 healthy，
> `curl http://localhost:8080/health` 通，管理员登录返回 `code=OK` 与 token。

---

## 背景

服务器为 Linux，已安装 Docker + Docker Compose，且已成功部署过本项目的旧版本：
仓库根目录已有 `.env` 配置文件、MySQL 数据卷（`mysql-data`）、旧容器。
本次只需拉取最新代码并重建容器，**不要**重新安装任何软件、不要手动改数据库。

## 前置信息

- 仓库根目录：`career-planner/`（`docker-compose.yml`、`docker-compose.override.yml`、
  `Dockerfile` 与其同级）。
- 目标分支：`main`（如需部署其他分支，把下面步骤 1 中的 `main` 整体替换）。
- 以**根目录**的 `docker-compose.yml`（＋`docker-compose.override.yml` 本地构建）为准；
  `deploy/docker-compose.yml` 是过期骨架，**不要用它**。

## 执行步骤

### 1. 拉取最新代码

```bash
cd career-planner
git status --short
git checkout main
git pull origin main
git log --oneline -3
```

- 若 `git status --short` 显示有未提交的本地修改：先停下来报告，由人确认后再继续，
  **不要**自行 `reset --hard` / 丢弃他人改动。
- 若 `git pull` 冲突：同样停下来报告，不要强行覆盖。

### 2. 检查 `.env` 必需变量是否齐全

参考根目录 `.env.example` 与 `deploy/env.example`（注意：两份示例取**并集**才完整）：

`MYSQL_PASSWORD`、`MYSQL_ROOT_PASSWORD`、`GATEWAY_API_KEY`、
`JWT_SECRET`（≥32 字节随机串）、`DOCKER_IMAGE`（本地构建时可写占位值如 `career-planner-app:local`）。

- 若 `.env` 已存在且历史上启动无报错：只补缺失项，直接跳过本步其余内容。
- 只有缺变量才补充；**不要改动已有的真实密码/密钥，否则数据连不上**。
- `GATEWAY_API_KEY` 是 career-ai 与后端共用的网关鉴权密钥，两边必须一致
 （compose 内 `AI_GATEWAY_API_KEY` 直接引用它）。

### 3. 重建并启动（本地构建，无需推送镜像）

```bash
docker compose -f docker-compose.yml -f docker-compose.override.yml up --build -d
```

说明：

- 前端已随根 `Dockerfile` 打进后端 jar，career-ai 代码随镜像构建 COPY 进去，无需单独部署。
- 后端启动时会自动幂等执行数据库 schema 迁移与种子数据，无需手工执行 SQL。
- 首次构建需拉取基础镜像、耗时较长属正常；升级不影响 MySQL 数据卷，旧数据自动保留。

### 4. 验证（全部通过才算部署成功）

```bash
docker compose ps
# 期望：mysql、career-ai、app 均 Up 且 healthy

curl -s http://localhost:8080/health
# 期望：后端存活（有输出）

curl -s -X POST http://localhost:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"account":"admin","password":"Admin@2026"}'
# 期望：返回含 code=OK 与 token（若首次登录提示改密，属预期流程）
```

把以上三条命令的**实际输出**逐条贴出来对照，只有三条全符合预期才报告成功；
任一条不符则进入下面的注意事项排查，修好后重跑本步。

## 注意事项（排错手册）

- 若 mysql 刚启动、`docker compose ps` 显示 starting：属正常，等 healthcheck 转 healthy
  即可（最多等约 2 分钟），不要反复重建。
- 若 career-ai 容器启动失败：多为 `GATEWAY_API_KEY` 缺失或与 `.env` 不一致，
  回到步骤 2 核对（只读比对，不要把密钥原文贴到日志/对话里）。
- 若服务起来但 AI 调用报错：多为 `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL`
  配置问题；无 LLM key 时服务照常启动、`health` 照常 200，只有 AI 调用失败——属预期，
  不要当成部署故障。
- 若 8080 端口被占：`docker compose ps` 查看是否有旧容器冲突，
  必要时 `docker compose down`（默认保留数据卷）后再重建。
- 全程**不要**：重装软件、手动改数据库、改动已有真实密码、提交/外传任何密钥文件
  （`.env`、`career-ai/.env`）。
